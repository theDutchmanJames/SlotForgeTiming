# Race rule plugins — API 1

The fourth plugin milestone adds **bounded race rules**, selected under **Race Setup → Rules and Systems → Plugin race rules**. A setup chooses one rule plugin, so competing rule writers cannot silently override one another. None preserves the existing engine behaviour.

Install, configure and start the plugin in App Settings → Plugins before opening a new race. Its standard plugin settings are used for that new race. The ready screen identifies the frozen rule set. Rule plugins are not supported in Time Token Sessions; a setup that selects one is rejected rather than ignoring it.

## Execution model

The executable Node plugin runs `rules(context)` once, **before racing**, with a two-second deadline. It returns a data-only program. The app validates, copies and freezes the program, package fingerprint, version and settings, then runs its bounded expressions synchronously in the existing engine. There is no worker callback, IPC request, timer or network dependency at each sensor crossing.

This is intentionally a defined API, not arbitrary replacement of engine functions. API 1 supports fuel/tyre consumption modifiers, per-lap time consequences and competition-point bonuses. It does not expose arbitrary event listeners, power commands, forced pit actions, custom finishing conditions or full replacement classification algorithms. Timing and display plugins retain their separate APIs. Authors may calculate a program using executable code during preparation, but cannot inject renderer JavaScript through it.

A failed, malformed, missing, stopped or timed-out plugin blocks preparation of a new race. After successful preparation the executable worker is no longer required for rule evaluation. Worker failure cannot change the frozen rules. It may still require pausing if the same plugin is also the timing driver; the timing API handles that independently.

## Manifest and module

```js
// Optional manifest property; absent on legacy packages.
rules: { api: 1, label: 'Club challenge', description: 'Your explanation' }

// main.cjs — context.settings comes from the normal plugin settings schema.
exports.rules = context => ({
  fuelMultiplier: context.settings.fuel,
  tyreMultiplier: 1,
  lapTimeMs: {
    op: 'if', args: [
      { op: 'lt', args: [{ var: 'lapMs' }, 10000] },
      2000, 0
    ]
  },
  points: { op: 'mul', args: [{ var: 'lap' }, 1] }
});
```

Omitted fields default to `1`, `1`, `0`, `0` respectively. Unknown fields/operators are errors. The package example is generated by `tools/fixtures/rule-plugin.cjs`; it is a separately installed demonstration, not enabled or shipped as a user rule.

## Order and effects

1. Existing formation-lap, minimum-lap and Service Stop sensor gates run first.
2. Fuel and tyre multiplier expressions receive the same snapshot from before the accepted crossing. Built-in Fuel, Balance of Power, Weather, Push & Save and tyre-temperature calculations still run in their normal order. The plugin multiplies the resulting consumption by a factor clamped to **0–10**. An absent or disabled system stays absent/disabled. Existing out-of-fuel and worn-tyre retirement/no-lap rules still apply.
3. A counted crossing stores its raw duration unchanged. A valid lap may add **0–3,600,000 ms** of rule time, rounded to integer milliseconds. Pit laps, resumed/red-interrupted laps and laps above the track maximum do not receive this consequence. Every counted lap stores its factors and consequence in `car.pluginLaps`.
4. Rule time is added to effective race time alongside native penalties and director adjustments. Best laps, personal bests and track records use raw eligible times. Practice and qualifying still rank by best legal lap.
5. The `points` expression is an additive competition bonus, rounded to two decimals and clamped to **−10,000…10,000**. It does not change the penalty-point counter. It contributes to points-based heat/class scoring and championship awards; the ordinary classification and existing tie rules remain authoritative. It has no standalone race-points winner mode. Disqualified, retired, virtual and no-lap entrants receive no bonus. For class results, `position` means overall position, not class position.

Heat summaries retain the bonus, respecting counted/best/dropped/average heats and final selection when contributing the bonus to a championship. Championship guest eligibility, sprint scaling and team allocation apply normally. This is a bonus to each separate competition's points calculation, not a replacement for its points table.

## Expressions and inputs

An expression is a finite number, `{var:'name'}`, or `{op:'name',args:[...]}`. Maximum depth 8 and 96 nodes per expression; numbers and intermediate results are bounded to ±1,000,000,000. Division by zero returns zero. Operators:

| Operator | Arguments | Meaning |
| --- | --- | --- |
| add, sub, mul, div, min, max | 2 | Arithmetic |
| lt, gt, eq | 2 | Comparison; returns 0 or 1 |
| and, or | 2 | Numeric truth values; returns 0 or 1 |
| if | 3 | Condition, true branch, false branch; only the chosen branch is evaluated |
| abs, floor, round | 1 | Absolute value or rounding |

Variables: `base` (1), `lane` (one-based), `lap`, `lapMs`, `medianMs`, `averageMs`, `bestMs`, `totalMs`, `fuel`, `tyreLife`, `penaltyPoints`, `position`, `wet`, `yellow`, `pit`, `valid`.

Before a crossing, `lap` is the candidate completed-lap number and `lapMs` its raw duration. History statistics use the last 100 eligible laps **before** this crossing (no invalid, removed, slow or pit laps). Missing history is zero. `totalMs` is race time at the crossing. `fuel` is remaining fuel in the system's units; `tyreLife` is percent. Boolean inputs are 0/1; `wet` is true only in Wet weather. Yellow alone does not invalidate a lap; a plugin can explicitly branch on it.

For points, `lap` is the current number of driven laps and `position` the native overall classification. History includes the current result. `lapMs` is zero and weather/pit flags use their default zero values. Points formulas should use result/history variables, not crossing-only flags. An invalidated lap still counts toward distance; a physically removed lap does not.

## Review, persistence and recovery

Lap review can invalidate or remove a lap. Its rule-time consequence then no longer contributes; fuel and tyres already consumed remain historical. Physically removing a lap also removes its corresponding `pluginLaps` entry. Director adjustments remain separate. The finalize page explains rule time and competition bonus.

Snapshots and sessions retain `rulePlugin` provenance and the program. Engine `rulesSnapshot.config.rulePlugin` and per-lap effects support deterministic recovery; heat results carry their plan too. Resume checks the installed package contents and requires the exact original version/fingerprint. It reuses the saved settings/program, never reruns preparation. A stopped worker is sufficient for this verification; the frozen plan is app-evaluated data. Changed or missing dependencies block resume until restored. A malformed or mismatched engine snapshot is refused. Viewing saved results does not require executing or installing the plugin.

Saved rows have `pluginPoints` and `pluginTimeMs`; standalone rows also retain `pluginLaps`. The existing `penalty` total includes native penalty time plus rule time, with `pluginTimeMs` identifying the rule component. Do not add that component twice. Raw lap records are unchanged. Backup/restore preserves these fields. Sharing a Race Setup preserves the plugin ID, but does not bundle or activate executable code.
