- **1.61.2**: **A change to the database is written to its file in the background, so the core no longer stands still for 280 to 390 ms at every save** (Dutch, Wed 21 Oct 10:29: "We will do 1.61.2 and then stop with improving the app and working out stalls. Full save to the background seems like a good decision but we have sped up the app's performance already quite a bit", after his two 1.61.1 reports from Windows at 10:21 and 10:25). **What the reports showed**: every stall of 100 ms or more in the sampled time was a full save of the database: 278, 313, 331 and 346 ms for saves of 353 to 384 ms (making the text 182 to 198 ms, writing the file 169 to 198 ms). The lists that go to the window came in bursts of 57 to 134 ms in all. **What changed** (`db.js`, `main.js`, `transfer.js`): (1) *Only what changed is made into text again.* The file used to be made by turning the whole database into text at every save. Now every item (a driver, a slotcar, a lap, a race ...) keeps the text it had at the last save (`this.texts`, a `WeakMap` keyed by the row), and a change to an item throws away that one text (`touch`; `update`, the cars of a finished race). The pieces of the file (`fileChunks`) put together are exactly `JSON.stringify(data, null, 2)`, so the file is the same as before and every older version reads it. Items over 200,000 characters are a piece of their own; smaller ones are grouped to about 500,000. Settings, extra fields and the version are made again every time (they are small, apart from the settings' pictures, which have their own file since 1.61.0). (2) *The file is written by the system's helper threads* (`writeChunksAsync`): the pieces go in slices of at most a million characters (never between the two halves of an emoji) to `slotforge-timing.json.bg.tmp`, are flushed and closed, and renamed over the real file, all asynchronously: a synchronous rename over the old 150 MB file stood the core still for about 65 ms, because the system frees the old file in that call (my first build had 71 to 83 ms stalls from that). One write at a time; the changes that come meanwhile are written together by the next one (ten quick changes are two writes), and the text is made in one go at the start of a write, so the file is always one state of the database. A save in the program's own time (an import, a restore, the start) that comes while a background write is on its way is never replaced by the older text: the older write is dropped before its rename, or, when it is already renaming, the newest state is written once more right after. (3) *The answer waits for the file.* `db:add`, `db:update`, `db:remove`, `session:save`, `session:remove` and the three extra-field handlers answer the window when the file has the change, and a write that fails reaches the screen as an error as before; a finished race that could not be written is taken out again, with the counters of the cars (`saveSessionAsync`). (4) *Closing waits for the database write too* (`writesPending`, up to the same 3 s as for the settings). (5) *A restore and an import wait for a write that is on its way* and are written at once (`saveNow`: all or nothing, as before). A stale `.bg.tmp` of a stopped program is removed at the start. (6) *A tickbox*, **Save changes to the database in the background** in App Settings > General > Performance (on; only an explicit off turns it off, the core reads it at once): off is the old way, the core waits for the disk. (7) *The report*: the Database file line says how many saves were in the background, how long the core was busy (the text) and how long the file took; the note *Saved the whole database in the background: the core was busy X ms making the text, the file took Y ms* for a save of 20 ms or more; two notes tell what to do (switch it on, and why the text of a save can still take 100 ms or more). **Measured** (a made-up database of 150 MB with his table names, in this sandbox, which is about 3.5 times slower than his PC for this work: a full save takes about 1400 ms here against 375 ms there): the longest stall of the core when a driver is edited, a slotcar is edited, a race is finished or a driver is added was **1385 to 1612 ms before and 14 to 23 ms after** (adding up to 64 ms); the answer to the window comes 520 to 630 ms later, with the core free in between. The file is exactly `JSON.stringify(data, null, 2)` after every kind of change. **Not faster**: removing a driver, a slotcar, a race or an extra field still makes the text of everything again (560 to 600 ms here; the file part is in the background), and a restore and an import write in the core. **Costs**: the texts are kept in memory, about the size of the data again (about +155 MB for his file); closing the program may wait for the write (up to 3 s). **Rule for the code**: whoever changes an item in place must call `touch(item)` (or `touchAll()`, which `save()` does); an item that is not touched keeps its old text, also in the file. **Not tried in Electron, on Windows or on the Pi.** **Not done**, and not planned unless he asks: the report tidy-up (a burst of lists as one line, measuring from the start of the app), pictures and sounds as files of their own, keeping pictures out of the lists. **README**: the 1.61.1 text said to start "with the Performance line on"; that line only exists on the race screen, and the report is in App Settings > General > Performance. Corrected. **Tests**: new checks in `tests/db.test.js`, `tests/perf.test.js`, `tests/perfstats.test.js`, `tests/depth.test.js`, `tests/transfer.test.js` and `tests/package.test.js` (changed to the new form of the handlers); the code was broken on purpose 197 times: 193 caught, the other 4 cannot change the result (the text of everything is made again after removing a race although the cars that changed are already marked, the same for a restore whose data is all new objects, an early check in the restore handler that is made again after the wait, and a condition that is only true while a write is running anyway). The first pass caught 160 of 196; the 36 that got through were looked at one by one: the edges of a slice at the first and last character made of two halves, the sizes of the groups, the file closed and flushed, a half written file removed after a failure, a write that was replaced counted as a save, the answer of an older failed write coming back, the undo of a race not marking its cars, and others got tests, and 4 were left as they are..

- **1.61.0**: **Settings are kept in a file of their own and written in the background, and the Performance report tells about the database** (Dutch, Wed 21 Oct 09:08: "Do it, sounds good!", after the plan of 09:02; his database file is 147 MB). **Why**: the report of 1.60.8 showed the core of the app stuck for 325, 342 and 124 ms at the moments settings were changed. The cause: a setting was saved by turning the *whole* database into text (pretty printed) and writing it, flushing it and renaming it, in the core, before the program went on. The pictures and the sound sets are stored in the database as text, so a change of a colour cost as much as a change of a driver: measured with a made-up database, about 5 ms for every MB of pictures and sounds. **The settings file** (`db.js`): the settings now sit in `<database name>.settings.json` next to the database (`slotforge-timing.settings.json` next to `slotforge-timing.json`). A setting that is changed (`settings:set`, `Database.setSettingsAsync`) is changed in memory at once and written to that small file in the background by a `LatestWriter`: one write at a time, while a write is on its way only the newest text waits (the file only ever holds the latest state), everyone who asked is answered when the newer text is on the disk (or told why it could not be written), and a text that is already in the file is not written again. The answer to the settings screen comes when the file is written; the program itself does not wait for the disk. **Which one wins**: when the settings file is there it holds the settings. No settings file yet (the first start of 1.61.0): the settings of the database file are used and the file is made. A settings file that cannot be understood (damaged, or not a list of settings) is copied to `slotforge-timing.settings.damaged-<time>.json`, the settings of the database file are used and a good file is made; if the copy cannot be made the program does not start, and nothing is changed (as for the database file); a settings file that is there but cannot be read stops the start in the same way. **The database file stays complete**: every full save (a driver, a car, a race setup, a finished race, a lap) writes the current settings into `slotforge-timing.json` too, so that file alone is still a whole database, and an older version reads it as before. A restore from a backup (`replaceAll`) writes the settings of the backup to the settings file as well (otherwise the old settings file would have won at the next start); a restore that cannot be saved changes neither. Closing the program waits (at most three seconds) for the race save and for the settings file (`writesPending`, `writesIdle`; `main.js`, `before-quit`). The synchronous `setSettings` stays for tests and anything that cannot wait: it writes before it returns, or after a write that is on its way. **The Performance report** (`db.js` `dbStats`, `perfstats.js`, `renderer/perf.js`): three new lines after *Race save*: `Database file (1.61.0): 147.2 MB, 12 saved since the app started, last 913.5 ms (making the text 402.2, writing the file 511.3), slowest 1210.4 ms, 0 failed`, `Settings file: 5.1 KB, 9 written, last 1.8 ms, slowest 6.2 ms, 0 failed` and `Biggest parts of the database (counted, about): drivers 91 MB, laps 41.5 MB, ...` (the five biggest tables, found by adding up the lengths of their texts: nothing is turned into text or copied; kept for a minute so asking does not cost anything). Notes: a save of the whole database of 150 ms or more, and a save or settings write that failed. **Measured** (Node, this sandbox, which is slower than your PC: the same file gave 1050 ms here where your report shows 325 to 342 ms, so look at the ratio; made-up database of 147.3 MB with 40 drivers and 30 cars with pictures, 39 sound sets and 20 000 laps; the stall is the longest gap of a 5 ms timer): one change of a setting: before (1.60.8) **1053 ms**, now **5 ms**; ten changes one after the other: longest stall 2189 ms and 11 seconds lost altogether, now 6.5 ms and nothing lost; with a database of 69 MB: 577 ms before, 6 ms now. **Not changed**: a change to a driver, a car, a race setup, a finished race or a lap still writes the whole file (1204 ms here with the 147 MB file), and so does the start of the program (once). That is the next step (1.61.2: the full save in the background, with the text of each table kept) and waits for your go; the pictures and sounds are not moved into files either. **Tested**: new checks in `tests/db.test.js` (the first start, which file wins, a damaged or unreadable settings file, only the small file is written, no turning of the whole database into text, five changes in a row, a disk that refuses, the synchronous change during a background write, the restore, the closing, the writer on its own, the figures), `tests/perf.test.js`, `tests/perfstats.test.js` and `tests/resumeasync.test.js` (the closing now asks for both kinds of writes). The code was broken on purpose 92 times: 90 caught, the other 2 cannot change the result.
- **1.60.8**: **The other picture widgets use short links too, and the start lights' pictures are made ready before the race** (Dutch, Tue 20 Oct 23:44: "Do the short links for the other picture widgets and loading the start lights' pictures before the race"). **Why**: since 1.60.6 the start lights are written to the page as short links (`blob:` addresses of files made from the pictures) instead of the picture itself, which took a light that comes on from 160 to 190 ms to about 10. The same cost sits in every widget whose picture *changes* during a race: the page is given the whole picture as text again (a data address of 0.5 to 1 MB per picture) and has to read it and decode it before it can draw. And the first time a light came on, its file was made at that moment (4 to 11 ms on the processor of the test setup, more on a Pi). **Short links for the other widgets** (`renderer/widgets.js`, `renderer/weatherwidgets.js`): the pictures of the avatar, driver and team picture, and the slotcar picture (`avatarHtml`), the logo and image widgets (`imageHtml`), the race flag pictures (`flagImgHtml`), the fuel picture steps (`fuelHtml`) and the tyre, weather, wind and condition pictures (`weatherwidgets.js`, `pic`) now go into the widget text as `link(picture)`, the same call the start lights use (`PicMemo.link`: only for a picture over the size that counts as big, only with the links switched on; a small picture, a picture with an address, a window that cannot make files: the picture itself, as before). **The memo and the links** (`renderer/picmemo.js`): a text that was made with a link in it is kept in the memo of its widget; when the links change (a link let go because there are more than 256 or 256 MB, `clearLinks`, links switched on after they were off) a counter (`gen`) goes up and every text made before is made again the next time it is asked for, so a widget never gets a `blob:` address that has been released. **Pictures made ready** (`PicMemo.prepare`, `Widgets.prepareLights`): when the race screen (or the second screen) is built, the pictures of the Start lights widgets of the layout are put in a queue: the countdown first (each light off, then on), then the rest of the set, each only once, only the pictures that are big and not yet a link. One picture is made in each moment (`setTimeout` 0), so the screen is never kept for more than one picture, and each one is asked to decode once (`new Image().decode()`, nothing is done with the result; a window without `Image` or with a rejected decode is not stopped). The queue takes at most three quarters of what the links may hold (192 links, 192 MB), so what is in use is never let go to make room (`left`: pictures that had no room, they are made when they are needed, as before). Switching the links off or clearing them stops the queue (a counter on the queue: a moment of an old queue does nothing). The Performance report adds to its line about the short links: `made ready ahead of time: 5 (30.0 ms), 2 without room, 3 still waiting` (nothing when nothing was made). **In the test setup** (the real `index.html`, the processor slowed down 4 times, emulated graphics card: **not the Pi**; ten pictures of 700 px for the lights, 1000 px pictures for the rest; the runs vary by about 15% between repeats): *start lights*, per update of the lights widget in the countdown: before (1.60.7) 5 to 13 ms (of which the text 4 to 11), now 0.6 to 6 ms (the text 0 to 1); five pictures were made ready in 30 to 80 ms in five moments before the Start button was pressed; with the preparation switched off the cost is the old one (10 to 15 ms). *Fuel pictures* (two fuel widgets with ten 1000 px pictures per lane, two cars refuelling): the page writes of the fuel widgets went from 418 and 428 ms to 2 and 4 ms in 14 seconds, the longest update from 161 and 149 ms to 36 and 41 ms, the stuck-window messages (57 to 245 ms) from 4 and 6 to none, the update total from 1770 and 1710 ms to 1263 and 1286 ms. *Avatar and slotcar pictures* (they do not change during a race): no change you can measure (the average update 10.2 to 12.1 ms before, 11.3 to 12.8 ms now). Not measured on the Pi, in Electron or on Windows; whether the decode warm-up helps there is not known (in the test setup it cannot be told apart from the rest). **Costs**: a picture that is a link exists twice, as text in the data and as a file in the memory of the window (at most 256 MB of files). **Tests**: `tests/picmemo.test.js` (the links in every builder, a text with a released link is made again, switching the links on and off, the queue: order, one picture a moment, budget of three quarters of the links and of the bytes, stopping, asking again, a picture linked in the meantime, the time, windows without `Image`, `setTimeout`, files or decoding, the pictures of a lights set and of a layout), `tests/perf.test.js` and `tests/perfscreen.test.js` (the new part of the line and the figures), `tests/live.test.js` (the race screen hands the lights over).
